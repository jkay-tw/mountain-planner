# v0.7 — Node identity and candidate data audits

## Current milestone (staging only)
- Introduced `js/node-identity.js`: route-scoped, deterministic provisional IDs, independent of visible labels.
- Added tests proving that 玉山「主北岔路」 and 奇萊「主北岔路」 cannot be joined by string equality.
- Added `tools/audit_hiking_segments.py` to inspect a locally supplied candidate JSON and export conflict, duplication, shared-name and connectivity reports.
- Neither `main` nor the user plan JSON schema is modified by this milestone.

## Safety policies
1. Display names are not globally unique. Different route groups must remain isolated until explicitly linked.
2. The `route_id::encoded-name` key is a **provisional** internal key, not an approved permanent geographic ID. Renaming a node or splitting a route can change it. Assign durable `nodeId` entries and a reviewed identity registry before production migration.
3. True physical overlap across groups requires evidence and explicit mapping; never infer it from matching labels alone.
4. Keep `name`, `from`, `to`, minutes and old `schemaVersion:1` plan import intact until a tested migration is ready. Do not discard manual segment times.
5. Do not treat a passed structural audit as independent source verification. Do not automatically add third-party segments to the published database.

## Offline audit
Run from project root:
```
python tools/audit_hiking_segments.py "/path/to/hiking-segments.json" --out ./audit
```
Reports include `summary.json`, `cross_group_names.csv`, `conflicting_segments.csv`, `repeated_segments.csv`, `structural_issues.csv`, `group_connectivity.csv`.
